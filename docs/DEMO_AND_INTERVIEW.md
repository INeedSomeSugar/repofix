# 演示与面试说明

## 两分钟演示

1. 运行 `repofix serve`，打开 `http://127.0.0.1:8011`。
2. 选“CSV 空行与引号解析”，保持“固定回放”，点击“开始修复”。说明此模式检查工程链路，不调用模型。
3. 展开“复现原始测试失败”，看原实现如何把空行变成不完整记录。
4. 查看读取源码、修改文件和测试结果；右侧 diff 来自实际文件变化。
5. 查看独立评分和运行摘要。说明原始测试受保护、额外断言不提供给模型。
6. 选择“DeepSeek · 真实模型”运行，或者在左侧打开已有 DEEPSEEK 记录。展示模型选择的工具、实际轮数、token 和补丁。

不要把已有运行记录当作刚刚发生的调用。实际 API 可能产生不同工具路径、补丁、耗时和用量。

## 暂停恢复演示

```powershell
.\.venv\Scripts\python.exe -m repofix.cli run --case csv_records --provider replay --pause-after-turns 4
# 从输出复制 run_id。原源码已修改，任务处于 paused。
.\.venv\Scripts\python.exe -m repofix.cli resume <run_id>
```

恢复后保持同一 run_id、消息历史、累计预算和补丁。网页的“暂停”会在当前模型或工具调用结束后生效。

## 面试中应能解释的设计

- **为什么是 Agent？** 下一步读哪个文件、搜索哪个符号、怎样修改以及是否继续测试由模型根据工具返回值决定。权限和评分由程序固定。
- **怎样避免直接改测试过关？** 既有测试路径不能修改，原始文件逐次核验哈希；最终运行额外断言并要求源码确实改变。
- **怎样防止修复任务读取 API Key？** 测试子进程用环境白名单；模型工具只读取自带仓库内允许的文件；密钥不进入消息或 trace。
- **为什么精确替换而不直接覆盖整个仓库？** 修改范围明确，旧文本唯一匹配，容易定位冲突、生成 diff 以及恢复已完成的文件操作。
- **任务恢复如何处理重复修改？** 工具调用 ID 绑定请求签名及修改前后哈希，恢复时识别修改是否已经落盘。
- **反馈真的提高效果了吗？** 本轮20次合成开发试验，单次补丁10/10、反馈9/10，反馈token约3.4倍。失败案例中模型新增错误测试并受其反馈影响；更复杂冻结任务和保留集尚未建立。
- **目前最明显的工程边界？** Docker后端已完成真实CSV容器回放和清理验证，完整网络／挂载／超时／资源边界仍需专项测试。当前只接受内置可信样例。
